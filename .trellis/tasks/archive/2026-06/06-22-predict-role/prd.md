# Add predict role for falsifiable experiment predictions

## Goal

Close the "Reasoner-equivalent" gap in Chitking's role roster by adding a new role that proposes the next concrete experiment with an **explicit, falsifiable prediction** and a **cited source**. Today no Chitking role commits the research to "we predict X will happen because Y (source)" — `dreamer` only ideates, `plan` writes a prose plan, and `verify`/`oracle` reason about current state rather than about what will happen. Borrowing Scholar-Loop Reasoner's predict-then-verify spine — without abandoning Chitking's human-checkpoint model — is the single highest-leverage improvement available.

## What I already know

From `src/templates/chitking/config.yaml`, `src/commands/types.ts`, `src/commands/templates.ts`, `src/commands/commands.ts`:

- Roles are declarative YAML in `config.yaml` under `roles:` — shape `RoleDefinition = {prompt: {objective, stop_conditions[]}, min_stage?, min_readiness?, warnings[]}` (`types.ts:119-124`).
- 7 existing roles: `plan · dreamer · build · verify · synthesize · review · oracle`.
- Stage ladder: `seed → briefed → gap-identified → specified → verification-planned → implementation-ready → evidence-recorded → synthesis-ready`.
- `dreamer` already has a **special-case contract template** (`dreamerRoleContractContent` in `templates.ts:113`) because of its hard boundaries (ideation-only, cannot hand to build). This is the precedent for a role with extra structural rules.
- Role packets are generated by `buildRolePacket` (`commands.ts:287`) → written to `.chitking/contexts/<slug>/<role>.yaml` with fields `{role, warnings, prompt, agent_utilities}`.
- OpenCode adapters generated per role (`templates.ts:159` `opencodeAdapterContent`) → `.opencode/agents/chitking-<role>.md`, with `mode: subagent` and per-role permissions (`opencodePermissionsForRole`).
- Roles recorded via `ck-record` into thread sections; section map is `RECORD_SECTION_BY_TYPE = {evidence, failure, decision, revision}` (`types.ts:63`). No "prediction" section exists today.
- `ck-dispatch` CLI flag `--role <name>` already supports single-role dispatch; role list lives in the `--role` help text (`cli/chitking.ts:201`).
- Human owns stage/readiness transitions; all roles are advisory.

## Assumptions (temporary)

- The new role is named `predict` (TBD — first brainstorm question).
- It sits conceptually between `dreamer` (ideation) and `plan` (safe plan) — but stage-gating may differ (see Open Questions).
- Its output is a falsifiable prediction with a cited source, recorded somewhere queryable so `verify` can later check it (exact mechanism TBD).
- It must NOT replace `dreamer` or `plan`; it adds a missing function.
- It must respect Chitking's human-checkpoint model — no role changes stage/readiness automatically.

## Decision Log

**D1 — Output shape (RESOLVED): Option B — lightly-structured prose via a new record type.**
Add the role plus a new `prediction` record type in `RECORD_SECTION_BY_TYPE` and a new `Predictions` thread section. The role's contract specifies the expected labeled fields (`Claim`, `Source`, `Predicted Effect`, `Falsification Criterion`); predictions are recorded via `ck-record --type prediction`. Packet generation stays generic (no special-case template needed in v1). `verify` can later quote `Falsification Criterion` lines without code changes.

**D2 — Role name (RESOLVED): `predict`.**
Internal consistency: `predict` role → `prediction` record type → `Predictions` section → `--type prediction`. Signals the unique function (falsifiable prediction), distinct from `dreamer` (no commitment) and `plan` (no prediction).

**D3 — Stage gating (RESOLVED): `min_stage: gap-identified`, `min_readiness: 2`.**
Earliest stage where Verification Obligations exist. predict's output (prediction + falsification criterion) feeds the transition toward `specified` and gives `verify` something to check later. Positions predict between `plan` and `verify`.

**D4 — Contract template & hard boundaries (RESOLVED): Option B — special-case template like `dreamer`.**
Add `predictRoleContractContent` in `templates.ts` with two extra sections mirroring dreamer's structure:
- **Required Output Shape** — the four labeled fields: `Claim`, `Source`, `Predicted Effect`, `Falsification Criterion`. Any agent reading the contract knows exactly what to emit.
- **Hard Boundaries**:
  - `predict → build` forbidden without `plan`/`review` intermediation (mirrors `dreamer → build`).
  - predict output must not be presented as an approved next safe action.
  - Cite-or-abstain: no `Source` = stop_condition triggers; no `Falsification Criterion` = stop_condition triggers.

Mirror dreamer's enforcement: `roleName === "predict"` branches in the contract dispatcher (the `defaultRoleContractContent` / `dreamerRoleContractContent` fork at `templates.ts:256-260`) and in `opencodeAdapterContent` (the dreamer-boundary conditional at `templates.ts:165`). Packet generation (`buildRolePacket`) stays generic.

**D5 — verify wiring (RESOLVED): Option B — light nudge via a verify warning.**
Add one line to verify's `warnings[]` in `config.yaml`: `"When checking obligations, cite specific Falsification Criteria from the Predictions section when available."` Config-only change, no code, no test restructuring. Closes predict→verify by convention *and* by contract signal. verify's `objective` and `stop_conditions` stay focused on Verification Obligations.

**D6 — Permissions (RESOLVED): default tier + predictBoundary line (derived).**
predict falls through to the default permission tier in `opencodePermissionsForRole` (`templates.ts:122`) — read-only, no `edit`, no `bash`, no `task`. Rationale: predict is advisory (like `dreamer`/`plan`/`review`/`oracle`), and deliberately does NOT get `bash` (giving it bash would let it peek at results before committing, undermining predict-then-verify discipline). No code change to `opencodePermissionsForRole` itself.
Mirror dreamer's adapter enforcement: add a `predictBoundary` conditional in `opencodeAdapterContent` (`templates.ts:164-167`) sibling to `dreamerBoundary`, e.g. `"OpenCode `edit: deny` blocks write/edit/patch tools. Do not hand predictions directly to build/Executor; route through plan/review first. Do not present predictions as approved safe actions."`

**D7 — `ck-assess` stage criteria (RESOLVED): Leave `ck-assess` untouched.**
`stage_criteria` and `maturity_criteria` in `config.yaml` stay as-is. predict's value is delivered via the role contract + Predictions section alone. Coupling predict into stage advancement semantics is a separate decision worth evaluating after the role sees real use. No changes to `stage_criteria` / `maturity_criteria` / `ck-assess` behavior.

## Future Work (flagged, not in v1)

- **Calibration loop closure** — a future `prediction-outcome` record type linking evidence entries back to the predictions they confirm/refute, giving Chitking a soft calibration spine (human-curated, no frozen metric). Extension point: the v1 `prediction` record format should stay referenceable.
- **`ck-assess` coupling** — adding "Predictions: non-empty" as a stage criterion for `specified` or `verification-planned`, if real usage shows it should be load-bearing.
- **Multi-prediction threads** — the Predictions section supports a bullet list of labeled four-field blocks; no v1 limit on count, but future tooling may want to query/index individual predictions.

## Out of Scope (explicit)

- Auto-recording predictions from the role (still human/external-AI triggered via `ck-record`).
- Changing `verify`'s `objective` or `stop_conditions` (only its `warnings[]` per D5).
- Changing `stage_criteria` / `maturity_criteria` / `ck-assess` behavior (per D7).
- Calibration scoring / `prediction-outcome` record type (Future Work).
- Parallel population funnel / governor (orthogonal).
- Record-time schema enforcement for the four predict fields (contract-level only, per Chitking prose ethos).
