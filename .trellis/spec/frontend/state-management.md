# State Management

> Current state model for Chitking's CLI-facing workflow.

---

## Overview

There is no frontend local/global/server state library. Chitking state is file-backed and user-editable. The CLI reads and writes this state directly.

State ownership:

- `.chitking/` stores Chitking product state.
- `research/` stores user research content and source-of-truth Markdown.
- `research/<thread>/context/*.yaml` stores generated context packets and can become stale.
- `.opencode/` and `.codex/` files generated by `chitking init` are platform adapters, not canonical state.

---

## State Categories

| Category | Current files | Ownership |
|---|---|---|
| Product config | `.chitking/config.yaml` | Chitking-managed, user-editable |
| Active pointer | `.chitking/active.yaml` | Chitking-managed state |
| Role contracts | `.chitking/roles/*.md` | Canonical role contracts, user-editable |
| Project source | `research/project.md` | User research source of truth |
| Thread source | `research/<thread>/thread.md` | User research source of truth |
| Generated packets | `research/<thread>/context/*.yaml` | Cache/context generated by `chitking pack` |
| Platform adapters | `.opencode/agents/chitking-*.md`, `.opencode/commands/ck-*.md`, `.opencode/skills/...`, `.opencode/plugins/...`, `.codex/config.toml`, `.codex/skills/ck-*/SKILL.md` | Generated convenience adapters |

## When to Use Global State

There is no in-memory global state. Pass `cwd` explicitly into command functions, defaulting to `process.cwd()` only at the public command boundary:

```ts
export function chitkingFocus(
  thread?: string,
  cwd: string = process.cwd(),
): string | null {
  // ...
}
```

This keeps tests deterministic with temp directories and avoids hidden process-wide state.

---

## Server State

There is no server state. The closest external state is Git metadata read by `readGitSnapshot()` and `resolveCommit()` via `execFileSync()`. These are read-only probes except when tests initialize temporary Git repositories.

Generated context packets include `source_thread_updated_at` so Chitking can detect when packet state is stale relative to `thread.md`.

---

## Derived State

Derived state should be recomputed from source files rather than stored as truth:

- Role gate warnings come from config + thread frontmatter via `roleRiskWarnings()`.
- Next maturity suggestions come from `config.maturity_ladder` and current thread maturity.
- Stale packet warnings come from comparing packet `source_thread_updated_at` with thread `updated_at`.

Example from `chitkingOrient()`:

```ts
const riskyRoles = Object.entries(config.roles)
  .map(([roleName, role]) => ({
    roleName,
    warnings: roleRiskWarnings(role, config, thread.frontmatter),
  }))
  .filter((role) => role.warnings.length > 0);
```

---

## Common Mistakes

- Do not cache canonical research state in generated packets.
- Do not store active thread state in module globals.
- Do not treat `.opencode/` or `.codex/` adapters as canonical role definitions.
- Do not let an agent or generated adapter silently change maturity/readiness.
- Do not read `research/<thread>/thread.md` before `research/project.md` when acting as a Chitking role.
